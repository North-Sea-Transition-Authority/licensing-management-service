# Spike: Dynamic Snap Point Spacing

## Problem

Snap points are rendered as a uniform grid via `SnapPointsLayer.vue` and `generateSnapPoints()` in `grid-utils.ts`. Spacing is currently static — the default per coordinate system (30 arc-seconds for ED50, 500 m for BNG) or an explicit `snapPointSpacing` prop.

At low zoom levels the fixed grid is already guarded by `getMinSnapZoom()` (zoom 11 for ED50, zoom 12 for BNG) to avoid memory overflow. But at high zoom levels the same fixed spacing is too coarse — the grid is sparse and not useful for precise coordinate entry.

The goal of this spike is to determine how to make spacing dynamic with zoom, and to design a selection-tracking strategy so that a future "click to select snap points to draw a line" feature does not lose selected points when the grid regenerates.

---

## Current Implementation

### Data flow

```
baseMap.ftl  →  data-* attributes  →  gis-all.ts  →  BaseMap.vue  →  SnapPointsLayer.vue  →  generateSnapPoints()
```

### Props

`BaseMap.vue` exposes `snapPointSpacing?: number` and passes it straight down to `SnapPointsLayer.vue`. The FreeMarker macro and `gis-all.ts` do not currently wire this prop — it is only settable programmatically.

### Spacing defaults (`grid-utils.ts`)

| CRS  | Default spacing | Unit        |
|------|-----------------|-------------|
| ED50 | 30              | arc-seconds |
| BNG  | 500             | metres      |

### Point IDs

Each point ID is generated by `createGridPointId(indexX, indexY)` where both indices are derived from the current `gridSpacing`. The same physical location produces a different ID when spacing changes — this is the root cause of the selection-tracking problem.

### Regeneration triggers (`SnapPointsLayer.vue`)

- Map view initialises → immediate `regenerateSnapPoints()`
- `change:resolution` or `change:center` events → debounced (200 ms) `regenerateSnapPoints()`
- `srsWkid` or `snapPointSpacing` prop changes → immediate `regenerateSnapPoints()`

---

## Proposed Approach

### 1. Zoom-to-spacing tiers

Add a `getSpacingForZoom(zoom: number, srsWkid: SupportedWkid): number` function in `grid-utils.ts`. Use discrete tiers rather than a continuous formula — predictable behaviour, snaps to round numbers, easy to tune.

Suggested starting values (to be validated against the test page):

```typescript
// ED50 — arc-seconds
zoom 11 → 60   // 1 arc-minute
zoom 12 → 30   // current default
zoom 13 → 15
zoom 14 → 10
zoom 15 → 5

// BNG — metres
zoom 12 → 1000
zoom 13 → 500  // current default
zoom 14 → 250
zoom 15 → 100
```

### 2. SnapPointsLayer.vue changes

Track current zoom as reactive state. In the existing `change:resolution` listener (already debounced 200 ms), read `view.getZoom()` and store it. Derive a `computedSpacing` computed property:

```typescript
const currentZoom = ref<number>(0)

const computedSpacing = computed(() =>
  getSpacingForZoom(currentZoom.value, props.srsWkid)
)
```

Pass `computedSpacing.value` to `generateSnapPoints()` in place of `props.snapPointSpacing`.

### 3. Prop behaviour

We will remove the `snapPointSpacing` prop. There will be no override for the default spacing, and it will all be driven by the zoom level.

## Selection Tracking Design

### The problem

Current point IDs are `"${indexX},${indexY}"` where both indices are computed using the active `gridSpacing`. When spacing changes on zoom, the same physical location gets a different index and therefore a different ID. Any Set of selected IDs becomes stale the moment the grid regenerates.

### Fix: stable IDs from SRS coordinates

Change `createGridPointId` to use the point's canonical SRS coordinate pair instead of grid indices:

```typescript
// Current:
createGridPointId(indexX, indexY)  // "48,23"

// Proposed:
createGridPointId(srsX, srsY)  // "252500,602500" or "30.5000,62.0000"
```

Round to the finest meaningful resolution (1 arc-second for ED50, 50 m for BNG) so floating-point noise does not create duplicate or drifting IDs. Coarser spacing tiers are a strict subset of the finest grid, so IDs are stable across all tier changes.

### Selection state

```typescript
const selectedPoints = ref<SelectedPoint[]>([])
```

Selected points always live on a dedicated layer, rendered from their stored coordinates regardless of the current snap grid. When `snapPoints` regenerates the selection layer is unaffected.

```typescript
interface SelectedPoint {
  id: string
  originalSrsCoordinates: [number, number]
  wgs84Coordinates: [number, number]
}
```

Storing coordinates alongside the ID means the selection layer can render without any reference to the current snap grid.

### Two-layer rendering

The snap grid layer and the selection layer are separate concerns:

- **Snap grid layer** (`SnapPointsLayer.vue`) — renders the current zoom tier; knows nothing about selection state.
- **Selection layer** — always renders all selected points at their stored coordinates with a distinct style (e.g. larger circle, different colour).

When the grid regenerates on zoom, only the snap grid layer redraws. Selected points stay put.

**On overlap:** when the grid is fine enough to include a selected point's location, both layers render a point there. The selection layer sits on top with its distinct style, so the overlap is not a problem. This is simpler than filtering selected IDs out of the snap grid, which would couple the two layers.

## Future Considerations

### Layer type influence on spacing

If a future `layerType` prop needs to affect snap point density, prefer we might want to consider a **multiplier** approach over a new per-type tier table:

```typescript
getSpacingForZoom(zoom, srsWkid) * spacingMultiplierForLayerType(layerType)
```

This keeps the zoom-tier logic in one place. A `blocks` layer might use `2×` (coarser, aligned to block boundaries); a `detail` layer might use `0.5×` (finer). The alternative — a full tier table per `CRS × layerType` combination — is harder to maintain and easy to let drift out of sync.
